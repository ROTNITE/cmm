# Аудит архитектуры проекта CMM

Дата: 2026-05-08

## Проблемы

### 1. Инструментированные дубликаты (7 файлов)

**Проблема:** Для логирования создаются обертки `*_instrumented.py`, которые дублируют оригинальные файлы и усложняют поддержку.

**Найденные файлы:**
- `Lib/AI_request_instrumented.py` - обертка над `AI_request.py`
- `Lib/state_machine_instrumented.py` - обертка над `state_machine.py`
- `Lib/expert_agent_instrumented.py` - обертка над `expert_agent.py`
- `Lib/meta_moderator_instrumented.py` - обертка над `meta_moderator.py`
- `Lib/plan_development_instrumented.py` - обертка над `plan_development.py`
- `Lib/agent_moderator_instrumented.py` - обертка над `agent_moderator.py`
- `Lib/plan_critic_instrumented.py` - обертка над `plan_critic.py`

**Используются в:**
- `cmm/eval.py` - импортирует инструментированные версии
- `Lib/orchestrator.py` - использует `state_machine_instrumented`
- `Lib/direct_answer.py`, `Lib/json_retry.py`, `Lib/agent_improver.py`, `Lib/Finish_agent.py`, `Lib/Start_formalization.py` - используют `AI_request_instrumented`

**Решение:**
- Объединить оригинальные и инструментированные версии
- Добавить опциональный параметр `enable_logging=True` в оригинальные функции
- Удалить все `*_instrumented.py` файлы

---

### 2. Два логгера с дублирующей функциональностью

**Проблема:** Два отдельных логгера делают похожие вещи, что создает путаницу.

**Файлы:**
- `Lib/eval_logger.py` (8.6K) - детальное логирование AI вызовов
- `Lib/eval_logger_enhanced.py` (8.4K) - высокоуровневое логирование событий

**Дублирование:**
- Оба имеют методы: `case_start`, `case_end`, `stage_start`, `stage_end`
- Оба пишут в `console_incremental.log`
- Оба имеют `case_logs` и `flush_case_logs()`

**Решение:**
- Объединить в один `Lib/eval_logger.py`
- Разделить на уровни логирования: `DEBUG` (AI вызовы), `INFO` (события)
- Использовать стандартный Python `logging` модуль

---

### 3. Legacy файлы (2 файла)

**Проблема:** Старые модули с устаревшей логикой и жестко прописанными значениями.

**Файлы:**
- `Lib/Start_formalization.py` - legacy формализация запросов
- `Lib/Finish_agent.py` - legacy полировка ответов

**Использование:**
- Используются только в `tests/test_docs_and_hygiene.py`
- Не используются в основном коде CMM

**Решение:**
- Удалить оба файла
- Обновить тесты, чтобы не зависели от них

---

### 4. Разбросанные дефолтные значения

**Проблема:** `deepseek-chat` как дефолтное значение в 26 местах по всему коду.

**Примеры:**
- `Lib/state_machine.py`: `model: str = "deepseek-chat"`
- `Lib/orchestrator.py`: `model: str = "deepseek-chat"`
- `Lib/expert_agent.py`: `model: str = "deepseek-chat"`
- И еще 23 места...

**Решение:**
- Создать `Lib/config.py` с централизованными настройками
- Заменить все дефолты на `config.DEFAULT_MODEL`
- Позволить переопределять через переменную окружения `CMM_DEFAULT_MODEL`

---

### 5. Отсутствие централизованной конфигурации

**Проблема:** Настройки разбросаны по коду (цены моделей, дефолтные значения, лимиты).

**Примеры:**
- Цены моделей жестко прописаны в `eval_logger.py` (строки 121-122)
- Дефолтные температуры, токены в каждом модуле отдельно
- Нет единого места для конфигурации

**Решение:**
- Создать `Lib/config.py` с:
  - `DEFAULT_MODEL = "kr/claude-sonnet-4.5"`
  - `MODEL_PRICING = {"kr/claude-sonnet-4.5": {"input": 3.0, "output": 15.0}}`
  - `DEFAULT_TEMPERATURE = 0.4`
  - `DEFAULT_MAX_TOKENS = 850`
